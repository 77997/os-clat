# DNS behaviour of a default OPNsense 26.7 for ipv4only.arpa (RFC 7050 discovery)

Checked 2026-10-11 by reading opnsense/core (master and stable/26.7), FreeBSD libc on opnsense/src stable/26.7, Unbound and dnspython sources. Nothing was run on a box.

## Verdict of the independent re-check: the claim holds

On a factory-default OPNsense 26.7, Unbound does not forward to the system's DNS servers: it is a full recursive resolver that works from the root servers, and it forwards only after "Use System Nameservers" is ticked under Services > Unbound DNS > Query Forwarding. The firewall's own resolver list puts 127.0.0.1 (Unbound) ahead of the DHCP/RA/manual servers, Unbound answers the ipv4only.arpa AAAA query with a valid empty reply, and the FreeBSD resolver library accepts that as final; it tries the next server only on a timeout or a server error, so the result would also change with Unbound's state. For the behaviour the design specified at the time (discovery through the DNS servers configured for the system from DHCP, RA or manual entry), the plugin should take the system's server list from core (get_nameservers(), or "configctl system list nameservers", which is the DHCP/RA/PPP-learned plus manual servers without 127.0.0.1) and ask those servers directly. This is derived from source code and public DNS lookups; nothing was run on a box.

Nothing was run on an OPNsense box. The sources were read again independently (local clone of opnsense/core master, the same passages on stable/26.7, FreeBSD libc from opnsense/src stable/26.7, Unbound master source, and live public DNS lookups on 2026-10-11), and each link of the author's chain was tested against them. None broke.

**Link 1: default Unbound is recursive, not forwarding (verified).**
- The factory configuration only switches Unbound on. It has no forwarding element.
- The forwarding switch ("Use System Nameservers") has no default value, so it is off on a new install.
- The setup wizard writes only the enable and DNSSEC settings. It can add one forward for the local domain to Dnsmasq on 127.0.0.1:53053, which is not a catch-all.
- The generator writes a catch-all forward zone only when that switch is on and the system has nameservers. Otherwise Unbound runs its iterator against the root hints.
- A common assumption, that Unbound forwards to the configured servers, is therefore wrong for the default: Unbound is a recursive resolver by design and forwards only when told to.

**Link 2: 127.0.0.1 is listed first (verified).**
- /etc/resolv.conf gets 127.0.0.1 first whenever a registered service listens on port 53 and the opt-out box is unticked.
- On a factory box that service is Unbound; Dnsmasq sits on 53053.
- The DHCP/RA/PPP-learned servers come next, then the manual ones. libc reads only the first three lines.

**Link 3: libc stops at an empty answer (verified).**
- The resolver moves to the next server only after a timeout, a socket error, or a SERVFAIL, NOTIMP or REFUSED reply.
- A valid reply with zero answers is returned to the caller and reported as "no data". Neither res_nquery nor getaddrinfo loops over servers.
- dnspython behaves the same way: it raises NoAnswer without trying the next server.

**Link 4: recursive Unbound returns an empty answer for ipv4only.arpa AAAA (likely, by reasoning).**
- Unbound master has no special handling of the name in its default local zones, AS112 list or DNS64 module, and OPNsense's generated configuration adds none.
- Public DNS returns "no error, no AAAA" for the name, and the delegation is provably unsigned, so DNSSEC validation does not interfere.
- The default access list allows localhost, so Unbound does answer.

**Two nuances the claim glosses over.**
- "Never" is true only while Unbound gives a valid answer. If Unbound is stopped, still starting, timing out or returning SERVFAIL, libc does move on to the ISP servers and would find the prefix. A library lookup is therefore dependent on Unbound's state, which is a further reason not to rely on it.
- That assumption is correct in one opt-in mode. With "Use System Nameservers" ticked, Unbound forwards everything to exactly the system list (DHCP/RA/PPP-learned plus manual), and an ordinary lookup would then likely return the ISP's DNS64 answer. That was not run. Two caveats apply: the default rebind filter strips AAAA answers in fc00::/8 and fd00::/8, so a NAT64 prefix in that space would be removed; and Unbound's own DNS64 option would return Unbound's prefix, not the ISP's.

A library lookup would also reach the ISP servers first when Unbound is disabled or when "Do not use the local DNS service as a nameserver for this system" is ticked. With Dnsmasq on port 53 it likely would too, since Dnsmasq forwards to the resolv.conf servers unless told not to.

**Meeting the specified behaviour.** Core's get_nameservers(), exposed as "configctl system list nameservers", returns exactly "the DNS servers configured for the system from DHCP, RA or manual entry", without 127.0.0.1. Asking those servers directly is the literal form of that behaviour and works in every configuration above. RFC 8880 section 7.1 asks for the same thing and names the loopback-resolver case. One detail: for a given interface, RA-learned servers are used only when DHCPv6 supplied none.

The first reading's side points on drill/host behaviour, the rtsold scope suffix and Dnsmasq's REFUSED reply were not re-checked.

## unbound-default-mode

No, not by default. On a factory-default OPNsense 26.7 Unbound is enabled, but as a full recursive resolver: it walks the DNS tree from the root servers itself and ignores the system's configured DNS servers. Forwarding is opt-in: Services > Unbound DNS > Query Forwarding > "Use System Nameservers", unticked on a new install. The common assumption that it forwards holds only once that box is ticked.

Why discovery through the system resolver fails: the firewall's resolver list puts 127.0.0.1 (Unbound) first, then the DHCP, RA and manual servers. Unbound, recursing by itself, finds that ipv4only.arpa really has only A records and replies "no error, no AAAA record". The FreeBSD resolver library takes that as final; it tries the next server only after a timeout or server error. The ISP's DNS64 servers are never asked, so the design author's claim is correct.

With the box ticked, Unbound forwards everything to that same system list and should pass the DNS64 answer through.

The specified behaviour is still easy to meet: OPNsense exposes exactly that list (manual plus DHCP/PPP/RA-learned servers, without 127.0.0.1) through get_nameservers() and "configctl system list nameservers". The plugin should query those servers directly.

### Not established

- Nothing was run on an OPNsense box. The generated /var/unbound/unbound.conf and /etc/resolv.conf of a real 26.7 install were not inspected, and Unbound's actual reply to an AAAA query for ipv4only.arpa was not observed.

- Timing dependence of the system resolver path: if Unbound is not answering (boot, restart, crash) or returns SERVFAIL (for example on an IPv6-only WAN before it can reach the root servers), libc does fall through to the next server and would reach the ISP's DNS64. So the system-resolver result can differ between boot and steady state. Not tested.
- With "Use System Nameservers" on and a mixed server list (ISP DNS64 plus an ordinary manual server), which answer Unbound returns and caches is not deterministic; not tested.
- Whether the default private-address filter really strips a DNS64 answer when the ISP's NAT64 prefix lies in fc00::/7 was not tested; the well-known prefix 64:ff9b::/96 is not in the default list.
- Administrator choices change the picture and cannot be assumed by the plugin: "Do not use the local DNS service as a nameserver for this system" removes 127.0.0.1 from resolv.conf; Unbound may be disabled; Dnsmasq may be moved to port 53; custom catch-all forwards or DNS-over-TLS entries send Unbound to third-party resolvers that are not the ISP's DNS64.
- How a catch-all custom forward / DoT entry interacts with "Use System Nameservers" in the generated files was not traced (the dot.conf template has no check for the checkbox; the manual says system nameservers are preferred).

## resolvconf-and-fallthrough

Nothing was run on a box; all of this is read from source (opnsense/core master and stable/26.7, opnsense/src stable/26.7, dnspython).

The design author's claim holds. On a factory OPNsense 26.7, /etc/resolv.conf lists 127.0.0.1 first (Unbound is enabled on port 53 and the opt-out is unset), then servers learned by DHCP/RA/PPP, then manually entered ones. FreeBSD libc uses only the first three.

The gap is the Unbound assumption: by default OPNsense's Unbound does not forward anywhere. It is a full recursive resolver working from the root hints. It forwards to the system nameservers only when Services > Unbound DNS > Query Forwarding > "Use System Nameservers" is ticked, which is off by default. So for ipv4only.arpa AAAA it should return a valid, empty answer.

Resolver libraries treat that as final. libc tries the next server only after a timeout, a connection error, SERVFAIL, NOTIMP or REFUSED; dnspython raises NoAnswer immediately. The `rotate` option only changes which server is asked first. So the ISP's DNS64 servers are never asked.

The specified behaviour is still simple to meet: `configctl system list nameservers` returns exactly the DHCP + RA + manual list, without 127.0.0.1. Query each of those directly. RA-learned link-local servers come as `fe80::x%ifname`, usable as is. RFC 8880 asks for this same behaviour.

## per-configuration-outcomes

No. On OPNsense, Unbound does not forward by default. It is a full recursive resolver: it walks the DNS tree from the root servers itself and never contacts the ISP's resolvers. It forwards only when Services > Unbound DNS > Query Forwarding > "Use System Nameservers" is ticked (off in the factory config) or custom forwarders are added.

The factory /etc/resolv.conf lists 127.0.0.1 first, then the DHCP/RA-learned servers. A library lookup of ipv4only.arpa AAAA goes to Unbound, which answers "name exists, no AAAA". That is a valid answer, so FreeBSD's resolver stops; it tries the next server only on timeout, SERVFAIL, NOTIMP or REFUSED. So S1 fails on a factory-default box.

Outcomes (S1 / S2 / S3):
(a) default: not found / found / found
(b) Unbound forwarding: found / found / found
(c) Google DNS64 added: not found / found / found (ISP prefix)
(d) override off: not found / found / found (Google's 64:ff9b::/96)
(e) Unbound off: found / found / found
(f) local DNS not used: found / found / found
(g) Dnsmasq: found / found / found
(h) Unbound DNS64: Unbound's own prefix / same / ISP prefix

Use S3: ask each server from core's get_nameservers() (DHCP/RA-learned plus manual) directly; first AAAA answer wins. It is the specified behaviour, literally, and works in all eight cases. Nothing was run on a box; this comes from source and documentation.

### Not established

- Nothing was run on an OPNsense box. A lab check on a factory 26.7 install would settle it: compare `drill AAAA ipv4only.arpa` with `drill AAAA ipv4only.arpa @<ISP server>` and look at /etc/resolv.conf.
- S1 on a factory box is not reliably 'not found': if Unbound is down, slow or returns SERVFAIL (for example at boot on an IPv6-only WAN), libc falls through to the ISP server and a prefix appears. That makes S1 intermittent rather than usable.
- S3 with an empty list (override disabled and no manual servers) has nothing to ask. Decide whether to fall back to the local resolver (S1) or report 'no DNS64 found'.
- Case (d) and any setup pointing at Google DNS64: the answer is always 64:ff9b::/96. If the ISP's NAT64 uses a network-specific prefix, 'follow the answer' yields an unusable prefix. Should the plugin check the prefix is reachable?
- Case (h): S1/S2 return the admin's local DNS64 prefix. It is correct only if the admin matched it to the ISP's NAT64.
- RA versus DHCPv6: on a reading of ifctl.sh, RA-learned DNS is only a fallback when DHCPv6 gives no DNS on that interface. If the ISP announces DNS64 servers by RA but different servers by DHCPv6, the RA ones would not be in the list. Not confirmed on a box.
- Multi-WAN: get_nameservers() without an interface returns servers from all interfaces, while RFC 8880 wants the resolver of the specific interface. get_nameservers($interface) drops manual servers not bound to a gateway (system.inc:459-461), which conflicts with the "or manual" of the specified behaviour.
- Edge case for (b) and (g): DNS rebinding protection may strip a NAT64 prefix inside ULA space. Unbound's default private-address list includes fc00::/8 and fd00::/8 (Unbound.xml:113, unbound.inc:227-235); dnsmasq's stop-dns-rebind (dnsmasq.conf template lines 4-7) blocks fd00::/8. Whether the Unbound defaults are actually written on a factory box was not confirmed.
- Case (b): the forwarder list is fixed when unbound.conf is generated. If get_nameservers() is empty at that moment, no forward zone is written (unbound.inc:306) and Unbound recurses until the next reconfigure.
- Not among the eight cases: Unbound with custom forwarders or DNS over TLS to a public resolver (dot.conf template) would make S1 fail the same way as the factory default.
- The official dnsmasq gitweb did not serve the source (it asked for a login); a GitHub mirror (imp/dnsmasq) was used for the two dnsmasq source facts, hence 'likely'.
- Line numbers refer to the master clone (commit 5de9cc0, 2026-10-10). For stable/26.7 the key lines of system.inc, unbound.inc and config.xml.sample were confirmed by fetch, but not their line numbers; dnsmasq.inc, the Dnsmasq template and the forms were read on master only.
- drill and host use their own resolver code rather than libc. The same result is expected for S1 but was not verified.
